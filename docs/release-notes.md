# Release notes

How to publish a downloadable build of Audio Editor, and what anyone downloading it
will actually experience.

> This is maintainer-facing documentation about the release *process*. It is not the
> per-release notes shown on the GitHub release page — those are generated by
> `tools/release.sh` for each version and are aimed at downloaders.

## How to publish

```bash
./tools/release.sh 1.0.0              # build + package + verify, no network writes
./tools/release.sh 1.0.0 --draft      # create a draft release to review
./tools/release.sh 1.0.0 --publish    # publish it
```

It builds a **universal** binary (Apple Silicon + Intel), and gates packaging on six
checks — signature, both architectures, stamped version, declared `.wav` handling,
and that the app actually launches. Output in `dist/release/`:

| Artifact | |
| --- | --- |
| `AudioEditor-1.0.0-macos-universal.dmg` | 717 KB, with a drag-to-Applications shortcut |
| `AudioEditor-1.0.0-macos-universal.zip` | 429 KB, archived with `ditto` (plain `zip` can drop the signature) |
| `SHA256SUMS.txt` | for verification |

Asset names deliberately avoid spaces, which GitHub would otherwise rewrite in the
download URL.

## The Gatekeeper problem

The stated goal is that someone can just download it and run it. **They cannot, not
without a fight.** The app is ad-hoc signed because there is no Developer ID
certificate (`security find-identity` reports 0), so Gatekeeper blocks it. Measured
on macOS 26.5.1 rather than assumed:

| Delivery | Measured behaviour |
| --- | --- |
| `.zip` | quarantine propagates to the extracted app; launching it is **`Killed: 9`** — not a warning, the OS kills it |
| `.dmg` | app is clean on the mounted volume, but **gains quarantine** when dragged to /Applications |
| after approval | runs normally |

So a downloader hits *"Apple cannot check 'Audio Editor' for malicious software"* and
must approve it once via **System Settings → Privacy & Security → Open Anyway**. The
Control-click → Open trick often cited online is **no longer in Apple's documented
flow**. The notes the script generates include these steps, so the instructions travel
with the download.

A technical user can bypass it with:

```bash
xattr -dr com.apple.quarantine "/Applications/Audio Editor.app"
```

which is verified to work.

One trap when testing this yourself: **`spctl --assess` reports `rejected` even for a
copy that launches fine.** It assesses the signature, not the quarantine exception.
Judge by whether the app runs.

## The three options

1. **Accept the friction** — publish as-is. Works, but a scary dialog for every
   downloader, and plenty will bail.

2. **Get a Developer ID** (US$99/year Apple Developer Program) → sign + notarise →
   **zero prompts**. Already wired up: `export SIGN_IDENTITY="Developer ID
   Application: ..."` makes `build.sh` sign with the hardened runtime, and it *fails
   loudly* on a bad identity rather than quietly shipping an ad-hoc build you would
   believe was properly signed. Notarisation is documented in `README.md` rather than
   automated, because it cannot be tested without a certificate.

3. **Ship source only.** For a project this size, `git clone && ./build.sh release
   run` takes about ten seconds and sidesteps the trust question entirely. If asking
   people to override their security settings feels wrong, this may be the honest
   default — binaries can still be attached for people who ask.

## What the release tooling consists of

- **`tools/release.sh`** — builds, verifies, packages and publishes. Has a dirty-tree
  preflight that refuses to release uncommitted work
  (`AUDIOEDIT_RELEASE_ALLOW_DIRTY=1` overrides it for testing).
- **`build.sh`** — accepts `AUDIOEDIT_VERSION`, `AUDIOEDIT_BUILD`,
  `AUDIOEDIT_UNIVERSAL` and `SIGN_IDENTITY`. Version stamps are applied to the
  *assembled* bundle so `Resources/Info.plist` stays a clean template.
- **`README.md`** — the "Publishing a release" section.
- **`AGENTS.md`** — the measured facts, so nobody re-derives them.
